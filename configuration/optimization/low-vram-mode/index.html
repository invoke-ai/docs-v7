Low-VRAM mode

Low-VRAM mode lets you generate with models larger than your GPU’s memory, such as the ~24GB unquantized FLUX.1 dev. Invoke keeps as many of a model’s layers in VRAM as fit and streams the rest from RAM as each step needs them.

On by default

Low-VRAM mode (enable_partial_loading: true) is on in every install, so there is nothing to turn on. It works on NVIDIA and AMD GPUs and on Intel GPUs, dedicated (Arc) or integrated. On Apple silicon and on the CPU, models load whole into system memory and the VRAM settings on this page do not apply.

Not sure which memory option fits your GPU and model? Start with Which memory option do I need?.

Platform notes

Section titled “Platform notes”

Some drivers move memory that does not fit in VRAM into much slower system memory instead of failing. Pick your setup to see what to change for it.

Notes that differ by operating system or GPU are listed for every setup, each labeled with the setup it applies to.

Operating system
GPU

Showing notes for

Windows · NVIDIA

Turn off the NVIDIA sysmem fallback. When VRAM fills up, the Windows driver moves memory into system RAM. That sounds like what Invoke does itself, but the driver’s version is not made for workloads like Invoke’s and slows generation down massively.

  1. Open the NVIDIA Control Panel.
  2. In the left panel, expand 3D Settings and click Manage 3D Settings.
  3. In the right panel, set CUDA - Sysmem Fallback Policy to Prefer No Sysmem Fallback.

Windows · AMD

AMD on Windows (ROCm). With a ROCm build of PyTorch (see the System Requirements), Windows behaves as if NVIDIA’s sysmem fallback were always on: an allocation that does not fit is moved into much slower system memory instead of failing, and stays there. Task Manager shows it as shared GPU memory. Invoke works around it:

  • The model cache plans against the video-memory budget Windows grants Invoke, not the card’s total VRAM.
  • The PyTorch allocator defaults to expandable_segments:True (see pytorch_cuda_alloc_conf under Settings), so fragmented VRAM does not push allocations out.
  • Decodes too large for the card are tiled before they start: waiting for an out-of-memory error does not work here, because none comes.
  • When at least 512 MiB of Invoke’s GPU memory stays in system memory after two generations in a row, the log says so (Windows kept … GiB of Invoke's GPU memory … in shared system memory). Other programs on the same GPU, such as games or browsers, can push Invoke’s memory out too: close them. If it keeps happening, lower the image size, set max_cache_vram_gb lower or device_working_mem_gb higher, and restart Invoke to get the memory back into VRAM.

Intel Arc, ARM64

Nothing to change for this GPU: the settings below apply as they are.

Linux · NVIDIA, AMD

Nothing to change for this GPU: the settings below apply as they are.

Apple silicon, Other / none

Models load whole into system memory here, so partial loading and the VRAM settings below do not apply. To use less memory, use a smaller build of the model: see the format comparison.

Settings

Section titled “Settings”

All of these go in invokeai.yaml and take effect after a restart. Most users need none of them.

The details of each:

enable_partial_loading: partial model loading

Invoke streams a model’s layers between RAM and VRAM as they are needed. When a step needs layers that are not in VRAM and there is no room for them, inactive layers are moved to RAM. To load every model whole instead, for example on a GPU with plenty of VRAM where that is faster:

device_working_mem_gb: working memory

Invoke keeps some VRAM free as working memory for the computation itself: 3GB by default, enough for most uses. If you still run out of memory, raise it:

Some operations know their needs in advance and ask for more. A VAE decode, which turns the generation’s output into an image, can need more than 3GB for a large image: Invoke calculates how much, and the model cache moves model layers out of VRAM until that much is free. The larger reservation lasts only for that operation. device_working_mem_gb is the floor: an operation never gets less.

reserve_vram_gb: VRAM kept outside the model cache

Keeps this much VRAM away from the model cache, for other GPU workloads the cache does not manage. It comes on top of device_working_mem_gb and any operation’s own request. To reserve 1GB:

max_cache_vram_gb and max_cache_ram_gb: cache sizes

Invoke caches models in RAM and VRAM so it rarely loads them from disk, and sizes both caches itself.

  • VRAM: unless you set max_cache_vram_gb, Invoke measures the free VRAM before each load, taking into account what other programs use (with a ROCm build on Windows, the budget Windows grants Invoke).
  • RAM: unless you set max_cache_ram_gb, the cache gets half your system RAM minus 2GB. On a machine with an NVIDIA, AMD or dedicated Intel GPU that is capped at the GPU’s VRAM minus device_working_mem_gb (or at max_cache_vram_gb if you set it), elsewhere at 32GB, and it is never below 4GB. The log shows the result at startup: Calculated model RAM cache size: … MB.

For example, on a 32GB machine with no other heavy programs, max_cache_ram_gb: 28 caches models aggressively, so they reload faster.

max_cache_vram_gb caps everything the cache plans for on the GPU: model weights, working memory and the reserve. See The VRAM budget before setting it.

keep_ram_copy_of_weights: a RAM copy of loaded models

On by default: Invoke keeps a RAM copy of every model’s weights while the model is in VRAM, which makes switching models and patching LoRAs faster. Turning it off lowers the average RAM use (the peak likely stays the same), at the cost of slower model switching and LoRA patching. On integrated Intel GPUs the setting is ignored, and the log says so once.

offload_on_architecture_switch: switching between model architectures

When a generation uses main models of another architecture than the previous one on the same GPU (say, FLUX.1 after SDXL), Invoke first moves every model the new generation does not use from VRAM to RAM. Models both use, such as a shared VAE or text encoder, stay. Moving models back costs a few seconds per switch, more with keep_ram_copy_of_weights: false. If you alternate between architectures that fit in VRAM together, turn it off:

clear_vram_after_session: clearing VRAM after every generation

After every queue item (every image of a batch), Invoke moves the models it holds in VRAM to RAM and hands the freed memory back to the GPU driver. The models stay cached in RAM, so each queue item then costs a few seconds to reload them, not a load from disk; with keep_ram_copy_of_weights: false also the time to copy them back to RAM. With several GPUs, handing the memory back briefly holds up a generation running on another GPU. On the CPU, Apple silicon and integrated Intel GPUs, whose VRAM is system memory, it changes nothing.

pytorch_cuda_alloc_conf: the PyTorch allocator

Configures PyTorch’s CUDA memory allocator, which can lower peak reserved VRAM. Using CUDA’s own allocator works well on many systems:

Unset, PyTorch’s defaults apply, with one exception: with a ROCm build of PyTorch on Windows, Invoke uses expandable_segments:True, because there fragmented VRAM makes Windows move allocations into system memory even when enough VRAM is free. Setting pytorch_cuda_alloc_conf, or any of the PYTORCH_ALLOC_CONF, PYTORCH_CUDA_ALLOC_CONF and PYTORCH_HIP_ALLOC_CONF environment variables, replaces that default. If PYTORCH_CUDA_ALLOC_CONF is already set to another value, it wins over pytorch_cuda_alloc_conf and the log warns about it. The options are explained in PyTorch’s documentation.

wan_memory_optimization: Wan video memory

Lowers Wan’s peak VRAM during denoising and decoding, at the cost of much slower generation and enough system RAM for the offloaded weights:

  • With partial loading on (the default) and an NVIDIA or AMD GPU, the Wan transformer keeps about 2GiB of its weights in VRAM and streams the rest from RAM. That trim may change nothing when the model cache already loaded no more than that. With enable_partial_loading: false the transformer stays fully in VRAM, but the other optimizations below still apply.
  • Pointwise transformer activations run in chunks, and the TI2V model’s per-token timestep conditioning is compacted.
  • An untiled VAE decode streams its chunks straight to the MP4. A spatially tiled decode keeps its usual full-tile path.

Chunked matrix operations add up in a different order, so the image is not guaranteed to be bit-identical at the same seed. wan_memory_optimization: false is the baseline path.

Developers can check the Wan VAE memory estimate on their GPU: see Wan VAE Memory Calibration.

pid_memory_optimization: PiD decode memory

PiD decodes straight into high-resolution pixels, so its activations and sampler can need more than a normal VAE decode’s working memory. Partial loading shrinks PiD’s weights but not these full-resolution intermediates. This setting processes parts of PiD’s pixel pathway in chunks and uses float32 instead of float64 sampler intermediates, for every PiD decoder. Measured on an RTX 4090, peak activation memory drops from ~3.7GB to ~1.5GB for a 2048px decode, and from ~0.9GB to ~0.5GB at 1024px. Speed stays about the same: chunking costs about 4%, which the cheaper sampler math mostly offsets.

device_working_mem_gb is the floor of the reservation, so to get the full saving at 1024–2048px, lower it as far as your GPU allows.

It is off by default because the output changes: the difference is small (around 43dB PSNR, indistinguishable side by side), but the same seed and workflow will not reproduce an unoptimized decode. The setting is server-wide and not recorded in image metadata, so each decode logs its resolution, patch-token count and whether chunking engaged (PiD memory optimization enabled for a … decode).

Calibrating a model’s working memory

Section titled “Calibrating a model’s working memory”

In the Model Manager, select a model, open Working memory and choose Calibrate.

Invoke’s decode estimates are measured on a few reference GPUs. Your GPU, driver and settings can need more or less. A calibration measures what a model’s VAE decode really takes on your GPU, and Invoke uses those measurements from then on.

  • What it runs: a few short text-to-image generations of the model at three sizes, up to the largest your GPU can decode in one piece with the VAE fully loaded in the memory free on it when the calibration is planned, in each VAE precision the model can decode in. Before each measured operation, Invoke moves the other models off the GPU, so the measured model is fully loaded. Each size runs once to warm up and twice more. The generations go through the normal queue, so they wait behind queued work and appear there like any other generation. Their images are intermediates: they never appear in the gallery or on a board, and Clear Intermediates removes them once the calibration has finished.
  • Who and where: administrators only. It needs exactly one GPU set as the generation device; with several, it is not available. One calibration runs on the GPU at a time: starting another while one runs, from another browser tab for instance, is refused until it has finished or you stop it. That includes the moment between two of its sizes: another administrator’s calibration whose page was closed holds the GPU for two more minutes. Your own interrupted calibration does not hold you back: starting a new one replaces it. If another calibration ran on the GPU in between all the same, the first one cannot go on: calibrate it again. If the model, or another model the calibration loads, is replaced or reinstalled while the calibration runs, the sizes still to come fail with a note to calibrate again, and the calibration counts as stopped: the sizes it already measured are discarded too, since they measured the model as it was before.
  • What it changes: decodes up to the largest size measured use the measured values, plus the same 5% margin the built-in values carry. Measurements that a fragmented GPU memory pool inflated, or taken while the VAE was only partly on the GPU, are left out, and the Model Manager shows those sizes as not counted. Larger decodes use whichever of the measured and the built-in estimate is larger. A tiled decode uses the measurements for each tile where they need more than the built-in values, and keeps the built-in values for what tiling adds. Other models that decode the same way (for example, SD1.5 and SDXL models when you calibrate an SDXL model) use the measurements too. Because the estimate decides when a large decode is split into tiles up front, a calibration can change which large images are decoded in tiles.
  • Where it applies: on this kind of GPU only (identical cards share it), and only while the software that affects memory stays the same: the operating system, the PyTorch and GPU runtime versions, the memory-related environment variables and Invoke’s memory settings. After such a change Invoke goes back to the built-in values until you calibrate again. A driver update keeps the measurements but marks them as possibly out of date until you calibrate again.
  • Stopping it: stopping a calibration started from the Model Manager, or clearing the queue while it runs, discards everything that calibration measured, the sizes that already finished included; the Model Manager shows those sizes as not counted because the calibration was stopped. Calibrate again to measure them. If a size fails for another reason, for example because the GPU runs out of memory at the largest size, the sizes that finished still count. A calibration run sent through the API without an attempt_id counts on its own instead: stopped, it keeps the sizes it measured. If they should not count, remove the run through the API (DELETE /api/v2/models/working_memory/runs/{run_id}), or reset the model’s calibration in the Model Manager.
  • What it does not cover: image-to-image and inpainting encodes keep the built-in values.
  • Reset: remove a model’s calibration from the Model Manager, or every calibration of this GPU; the change applies right away. Resetting one model removes only its own measurements: where other models’ measurements cover the same decode, those still apply, and the Model Manager shows which models measured it. Otherwise the built-in values apply again.

The measurements are stored next to the database in working_memory/<device class id>.json.

The VRAM budget

Section titled “The VRAM budget”

Most users should leave max_cache_vram_gb unset. If you set it, it caps everything the model cache plans for on the GPU, and the cache subtracts the working memory and the reserve from it before loading any model:

  • Set it no higher than the VRAM Invoke can actually use. A cap replaces the measurement of free VRAM, so memory other programs take is no longer accounted for.
  • A cap at or below device_working_mem_gb plus reserve_vram_gb leaves no room for models, which forces aggressive offloading. With device_working_mem_gb: 4 and reserve_vram_gb: 1, a 12GB cap leaves 7GB for models.
  • Most people who set it want Invoke to use much less VRAM, and set it well below their GPU’s VRAM.

Tiled VAE decode and encode

Section titled “Tiled VAE decode and encode”

Without tiling, the memory a VAE needs grows with the square of the image size: for FLUX.1, an untiled 3072² encode peaks at about 18.8GiB on an RTX 4090, a tiled one at 0.8GiB, and tiled memory grows far more slowly. It does still grow: while the tiles are assembled, the decoded tiles and two copies of the image are held at once, about 23 bytes per pixel in bf16, and the node’s latents and post-processing come on top. A 24576x24576 FLUX.1 decode at a 512 px tile measured 13.4 GiB on an RX 9060 XT and 16.5 GiB on an RTX 4090, and Invoke reserves at least that. Tiling costs some speed on smaller images, and a tiled result is not pixel-identical to an untiled one.

  • Automatic tiling starts only when an untiled decode would take most of the memory the GPU keeps resident, so it kicks in only for images too large for the card: for Z-Image on a 16GB GPU, from about 1850x1850 on NVIDIA and from about 1500x1500 on AMD, whose convolution library needs more memory. Anima tiles a little earlier, because its untiled decode pushes the Anima model out of VRAM on 8GB cards. Wan videos tile from 832x480 on 8GB cards and from 720p on 16GB cards.
  • Krea-2 decodes with the Qwen-Image Latents to Image node, so it follows that node’s settings and field.
  • MOSS-Image encodes and decodes with the FLUX.2 Latents to Image and Image to Latents nodes, so it follows the FLUX.2 row for decodes and encodes.
  • LTX-2 always decodes its video in tiles, sized by the node’s own Tile Size fields.
  • The Upscale panel turns tiling on by itself. Nodes with a Tiled field also have a Tile Size field.
Turning automatic tiling off

Decodes then run untiled unless tiling is requested. A decode too large for the card runs out of memory: the FLUX.1, FLUX.2 and Z-Image decodes retry tiled (the log says VAE decode ran out of memory; retrying with tiling), the others fail, and on Windows the driver may move the decode into system memory and run it very slowly instead. On a ROCm build under Windows, automatic tiling compares against the video-memory budget Windows grants Invoke, which is lower than the card’s total and lower again while another program uses the GPU.

Anima ignores this setting: there, tiling a large decode is what keeps the Anima model in VRAM, so untiled decodes would only be slower.

How different is a tiled image?

The VAE looks at the whole image at once, so the difference is spread over the image rather than limited to the tile seams. It is small: for a 1024x1024 FLUX.2 Klein image, 5.6 of 255 per pixel value on average, with no visible seams. But the same seed will not reproduce an untiled result exactly.

Windows page file

Section titled “Windows page file”

Invoke needs a lot of virtual memory (also called committed memory). On Windows this can hit the page file’s size limit, and Invoke crashes; issue #7563 has the technical details. The crash usually comes with Windows error code 3221225477, or with no error at all and an error 0xc0000005 (the same code in hex) in eventvwr.msc.

  • Make sure the disk has room for the page file to grow. Watch disk usage while Invoke runs: if it climbs to near 100% before the crash, this is very likely the cause. Free up disk space.
  • Make sure the page file is set to System managed size (the default), not a custom size, so it grows as needed.
