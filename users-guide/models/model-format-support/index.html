Model Format Support

InvokeAI recognizes a model’s format from the file itself, so you install every build the same way. This page lists which formats load for which model. What each format is, and how it behaves in memory, is explained under Quantized formats. Sizes, starter models and measured speeds are on each family’s own page.

Legend:

  • ✓ loads
  • L installs, but loading it for generation fails with a message naming the reason
  • R the install fails with a message naming the reason
  • ✗ not supported
  • – no such build exists

How an unsupported file fails depends on the file. Some are not recognized at all and install as an unknown model, with the reason only in the server log: the Diffusers layout of LTX-2 and the GGUF builds of MiniMax H3 and the Ministral 3B encoder. Others are recognized by their layer names and fail, or misbehave, only when they load.

The single-file CLIP builds are ComfyUI’s clip_l and clip_g, as used by FLUX.1 and SD 3. SD and SDXL take their CLIP encoders from the main model only, so a separate CLIP file does not change them. A CLIP-G file needs its text_projection for SD 3 and is refused without it, as are extended-context CLIP-L variants such as Long-CLIP. FLUX.1 takes CLIP-L only.

The Qwen3-VL GGUF encoder is the language model only; a separate mmproj vision file is refused, and split multi-part GGUFs have to be joined before installing. The Gemma-4 encoder installs as a folder (its config.json and tokenizer files next to exactly one weight file, bf16 or int8) or as a GGUF conversion of the LTX-2.5 encoder that packs its tokenizer and config in, such as elix3r’s or Rootport’s. Google’s stock Gemma-4-12B GGUF fails to install with a message, since LTX-2 needs the Lightricks-tuned weights; its mmproj file is not recognized. A standalone .safetensors file is not recognized.

The Qwen3.5 4B and 9B install as the same encoder type but are not interchangeable: Anima-3.8B takes only the 4B and MOSS-Image only the 9B, and each refuses the other. A 9B file must hold the whole language model: of a sharded export, the first shard is refused at install with a message and the others install as unknown models. Install the whole MOSS-Image Diffusers folder or a merged single file instead.

Quantized VAE files (fp8, int8, nvfp4) are not supported; use the unquantized VAE. The SD 3, FLUX.2, Qwen-Image, Qwen-Image-2.1, Wan, Anima and Ideogram 4 VAEs fail with a message when they load. The FLUX.1 and SD 1.x / SDXL single-file VAEs do not check, so a quantized file there fails with an unclear error or decodes incorrectly.

Preview decoders (Tiny AutoEncoders)

Section titled “Preview decoders (Tiny AutoEncoders)”

Tiny AutoEncoders render live denoising previews and nothing else. Each one is a single file, a .safetensors, .pth or .pt.

Both published layouts load: the decoder-only files (the *_decoder.safetensors files above, and the *_decoder.pth files ComfyUI keeps in models/vae_approx/) and the files that hold encoder and decoder together (diffusion_pytorch_model.safetensors, taef2.safetensors, taeqi2_1.safetensors).

TAESD and TAESDXL read the same 4-channel latents with the same network, and so do TAESD3 and TAEF1 with 16 channels. For these four the file name, its folder name or the download source has to name the TAE (taesd, taesdxl, taesd3 or taef1); a file that names none of them is refused (R). The starter models set the base themselves.

  • R: the “tinier” TAEQI2.1 (taeqi2_1_tinier); the message asks for taeqi2_1.safetensors instead.
  • Not recognized: other Tiny AutoEncoders, such as the 32× Sana decoder and the TAEHV video decoders (taew2_1, taew2_2, taeltx_2). They install as unknown models.
  • A Diffusers AutoencoderTiny folder (for example the madebyollin/taesdxl repository as a whole) installs as a VAE and is not used for previews. Install the single file instead.

FLUX.1 and FLUX.2 also accept ComfyUI/OneTrainer PEFT LoRAs whose module names start with diffusion_model.. Per-layer .alpha values in these diffusion_model. files set the LoRA scale.

For SD 1.x / 2.x and FLUX.2, LyCORIS LoKr files may store either Kronecker operand whole or as a factorized _a / _b pair. FLUX.2 also accepts LoHA files in the same BFL and kohya layouts.

PiD decoders load for FLUX.1, FLUX.2, SD 3, SDXL and Qwen-Image (v1 and v1.5, bf16 and int8 builds). FLUX.3 and MOSS-Image use the FLUX.2 decoders.
