Multi-User API Guide

यह कंटेंट अभी तक आपकी भाषा में उपलब्ध नहीं है।

Overview

Section titled “Overview”

This guide explains how to interact with InvokeAI’s API in both single-user and multi-user modes. The API behavior depends on the multiuser configuration setting.

Single-User vs Multi-User Mode

Section titled “Single-User vs Multi-User Mode”

Single-User Mode (multiuser: false or option absent):

  • No authentication required
  • All API endpoints accessible without tokens
  • Direct API access like previous InvokeAI versions
  • All content visible in unified view

Multi-User Mode (multiuser: true):

  • JWT token authentication required
  • User-scoped access to resources
  • Role-based authorization (admin vs regular user)
  • Data isolation between users

Authentication (Multi-User Mode Only)

Section titled “Authentication (Multi-User Mode Only)”

Authentication Flow

Section titled “Authentication Flow”

When multi-user mode is enabled, most API endpoints require authentication using JWT bearer tokens. The unauthenticated authentication endpoints are GET /api/v1/auth/status, POST /api/v1/auth/setup, and POST /api/v1/auth/login.

Authentication Process:

  1. Obtain Token: POST credentials to /api/v1/auth/login
  2. Store Token: Save the JWT token securely
  3. Use Token: Include token in Authorization header for all requests
  4. Refresh: Re-authenticate when token expires

Single-User Mode

When running in single-user mode (multiuser: false), authentication endpoints are not available and authentication headers are not required.

API Endpoint Changes

Section titled “API Endpoint Changes”

Authentication Required

Section titled “Authentication Required”

All endpoints now require authentication except:

  • GET /api/v1/auth/status — Check whether multi-user setup is required
  • POST /api/v1/auth/setup — Initial admin setup
  • POST /api/v1/auth/login — User login
  • GET /api/v1/images/i/{image_name}/full — Full-resolution image file
  • GET /api/v1/images/i/{image_name}/thumbnail — Image thumbnail
  • GET /api/v1/workflows/i/{workflow_id}/thumbnail — Workflow thumbnail

The image and thumbnail endpoints are intentionally unauthenticated because browsers load these resources via <img src> tags, which cannot send Authorization headers. Security relies on the fact that image and workflow IDs are UUIDs and therefore unguessable.

Error Responses

Section titled “Error Responses”

401 Unauthorized:

Occurs when:

  • Token is missing
  • Token is invalid
  • Token is expired
  • Token signature is invalid

403 Forbidden:

Occurs when:

  • User attempts admin-only operation
  • Account is disabled
  • Insufficient permissions

404 Not Found:

Occurs when:

  • Resource doesn’t exist
  • User doesn’t have access to resource

Board Endpoints

Section titled “Board Endpoints”

Boards are available to every authenticated user; what each caller may do to one is decided by their role on it.

List Image Boards

Section titled “List Image Boards”

Endpoint: GET /api/v1/boards/

Response:

This returns a paged response. See the swagger page (http://localhost:9090/docs#/boards/list_boards) for details. Each board describes the caller’s access to it:

  • general_access — the role every other user gets: restricted (none), viewer or contributor. Only the owner or an administrator may change it, with PATCH /api/v1/boards/{board_id}.
  • my_role — the caller’s own role: viewer, contributor, editor or owner; null when only administrator rights give access.
  • allowed_actions — the board actions the caller may take. Clients should decide what to offer from this list rather than from my_role.
  • admin_override — true when administrator rights give the caller more than my_role does.
  • owner_username — the owner’s display name. Administrators see the email of an owner without one; other users see Unknown user.
  • project_id — shown only to the board’s owner and administrators. An image or video DTO’s project_id likewise names the project it was made in only to that project’s owner and to administrators; everyone else reads null.

Only a board that does not exist answers 404. A board the caller cannot open answers 403 with the detail {"code": "board_unreadable", "message": "Not authorized to access this board"}, and an action the caller’s role does not allow answers 403 with the code board_action_denied and the message Not authorized to change this board: a refusal can be reversed by the board’s owner, so clients must not treat it as the board being gone, and the code tells lost access from a stale role without matching the message. A project’s inbox refuses renaming, archiving, moving, deleting and a change of general access with 409; those follow its project.

Deprecated

board_visibility is general_access under its pre-7.0 name (private = restricted, shared = viewer, public = contributor). It is still returned and accepted on update, but sending it together with general_access is refused with 422. It will be removed in 8.0.

Project Endpoints

Section titled “Project Endpoints”

Projects are private to the account that created them. The full save protocol, including the content and workspace halves and the schema floors, is described in Project Files (.invk).

Create a Project

Section titled “Create a Project”

Endpoint: POST /api/v1/projects

Creates the project and its inbox board and answers 201 with the record and workspace. The optional workspace field is the caller’s first workspace in the project, the workspace document itself (a create’s workspace is always the first row, so it carries no expected_revision), stored in the same transaction as the content, so no project is created without its creator’s workspace. It is checked as on PUT /api/v1/projects/{project_id}/workspace, except that the create’s max_canvas_schema_version covers it, and it needs minimum_document_schema_version at 4 or above: beside a whole document it is refused with 400 and the code workspace_needs_split_document, and nothing is created. The response’s workspace is the stored workspace (data, revision 1, updated_at), or null when the request carried none.

Save a Project

Section titled “Save a Project”

Endpoint: PUT /api/v1/projects/{project_id}

Saves the project’s content and answers with the record and workspace. The optional workspace field ({data, expected_revision}) stores the caller’s workspace in the same transaction and is for the save that splits a whole project (document schema 3 or older) into content and workspace: the raised document floor, the content and the first workspace row then land together or not at all. Its revision is checked as on PUT /api/v1/projects/{project_id}/workspace, and a mismatch refuses the whole save with 409 and the workspace’s current_revision. Omit it on every other save: a workspace sent with a save that leaves the document floor below 4 is refused with 400 and the code workspace_needs_split_document. The split cannot go without it either: a save that raises the floor from below 4 to 4 or above without workspace is refused with 400 and the code split_needs_workspace, so the split of a whole project never lands without the caller’s workspace.

Workspace saves declare max_canvas_schema_version (default 2) as well as max_document_schema_version; a client below the project’s canvas floor gets 412 with the code canvas_schema_unsupported.

Best Practices

Section titled “Best Practices”

Token Storage

Section titled “Token Storage”

Do:

  • Store tokens securely (keychain, secure storage)
  • Use HTTPS to transmit tokens
  • Clear tokens on logout
  • Handle token expiration gracefully

Don’t:

  • Store tokens in URL parameters
  • Log tokens in plain text
  • Share tokens between users
  • Store tokens in version control

Common Issues

Section titled “Common Issues”

Issue: “Invalid authentication credentials”

  • Token expired — re-authenticate
  • Token malformed — check token string
  • Token signature invalid — check secret key hasn’t changed

Issue: “Admin privileges required”

  • User is not an administrator
  • Use admin account for this operation

Issue: Token not being sent

  • Check Authorization header is present
  • Verify Bearer prefix is included
  • Check token isn’t truncated
