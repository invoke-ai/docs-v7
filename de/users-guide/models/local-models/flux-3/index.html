FLUX.3

Dieser Inhalt ist noch nicht in deiner Sprache verfügbar.

FLUX.3 Image Klein is a 5.6B diffusion transformer from Black Forest Labs that generates images from text and edits or combines up to ten reference images. InvokeAI supports both published checkpoints:

  • FLUX.3 Klein: step-distilled, for everyday use. Runs at 16 steps with CFG off (CFG Scale 1.0). It always samples without CFG, so Invoke is unavailable while CFG Scale is above 1.
  • FLUX.3 Klein Base: the undistilled checkpoint. Runs at 50 steps with CFG 3.5 and a negative prompt. It is meant mainly for fine-tuning and LoRA training, but generates normally too.

The variant is detected on install. A new FLUX.3 model starts with the defaults of its variant (steps, CFG, 1024×1024); when you switch from one variant to the other, use Reset all to model defaults in the Generate panel header to take over the new defaults.

License

Section titled “License”

Both checkpoints are released under the FLUX Kommunity License v1.0: non-commercial use, or commercial use for companies below US$5M in annual revenue. The Black Forest Labs repositories are gated: accept the license on the model’s HuggingFace page and add your HuggingFace token under API Keys in the Model Manager. The GGUF copies are not gated, but the same license applies.

This is a summary, not legal advice. Read the full license on the model’s HuggingFace page before using a model commercially.

Hardware

Section titled “Hardware”
Transformer buildTransformer sizeNotes
bf16 (Diffusers or single file)≈ 10.3 GiBreference quality
int8 (starter model)≈ 5.4 GiBstays int8 on every GPU
fp8r (Black Forest Labs)≈ 5.8 GiBwith FP8 Storage (switched on at install) or fp8_compute; ≈ 10.3 GiB otherwise
nvfp4 (starter model, or Black Forest Labs)≈ 4.9 GiB4-bit weights, decoded on every step
GGUF Q8_0 (starter model)≈ 5.6 GiBclose to bf16
GGUF Q4_K_M (starter model)≈ 3.1 GiBlowest VRAM; fine detail differs from bf16

The Qwen3-VL 4B encoder (≈ 8.5 GB as bf16, about half as fp8) and the FLUX.2 VAE come on top. The encoder runs before the transformer, so the two do not have to fit on the GPU at the same time.

Reference images add to the work per step. Measured on an RTX 4090 with the models already loaded, a whole 1024² image (text encoder, denoise and decode) with Klein bf16 at its defaults takes 6.5 s without a reference, 13.5 s with one 1 MP reference and 31.7 s with three. Klein Base at 50 steps and CFG 3.5 takes 36.7 s.

Speed and quality by build

Section titled “Speed and quality by build”

Measured on the same RTX 4090 (24 GB) with Klein at its defaults (16 steps, CFG 1.0) and 1024², three prompts with three seeds each:

BuildDenoise per imageWith int8 Compute / fp8_computeVRAM peakPSNR against bf16

int87.01 s4.07 s14.4 GiB33.2 dB; 34.5 dB with int8 Compute

fp8r (FP8 Storage on, as installed)6.61 s5.35 s15.0 GiB26.8 dB; 25.4 dB with fp8_compute

The VRAM peak is what nvidia-smi reports, text encoder and desktop included. The PSNR is the mean over the nine images. With fp8_compute on, the text encoder used here (a scaled-fp8 checkpoint) computes in fp8 too, so the PSNR values with the switches on compare against bf16 images made with that same encoder.

  • Closest to bf16 are int8 and GGUF Q8_0, then fp8r, then nvfp4. For the prompt with a sign, every build spelled its text correctly in all three seeds, with and without the compute switches. Without the switches, every quantized build scores its lowest per-image PSNR on the same seed of the sign prompt, whose letter colors shift in all of them, Q8_0 included.
  • Speed: without a compute switch, every quantized layer is dequantized on each forward, so on this card the quantized builds take up to 13 % longer than bf16. int8 Compute makes the int8 build the fastest, 1.52× as fast as bf16, and fp8_compute makes fp8r 1.16× as fast as bf16. Neither affects nvfp4 or GGUF.
  • Memory: the quantized builds peak about 5 GiB below bf16.

Installing

Section titled “Installing”

The FLUX.3 bundle in the Model Manager installs the GGUF Q4_K_M transformer, the Qwen3-VL 4B encoder and the FLUX.2 VAE. None of these are gated.

FLUX.3 needs three components:

ComponentDiffusers installGGUF / single-file install
Transformerbundledthe .gguf or .safetensors file
VAE (FLUX.2)bundledinstalled separately
Text encoder (Qwen3-VL 4B)bundledinstalled separately
  • Diffusers (black-forest-labs/flux-3-image-klein, black-forest-labs/flux-3-image-klein-base): an install of about 20 GB that bundles the VAE and the text encoder. Installing by repository id downloads only the Diffusers folders, not the single-file copy that sits next to them in the repository.
  • GGUF / single file: the file holds only the transformer. Install the FLUX.2 VAE and the Qwen3-VL 4B encoder as well. They are the same models FLUX.2 and Krea-2 use, so an existing install serves FLUX.3 too.

When you select a GGUF or single-file FLUX.3 model, pick the VAE and the Qwen3-VL encoder under Components if they are not filled in. A Diffusers model uses its bundled components unless you override them there.

Quantized single files

Section titled “Quantized single files”

Comfy-Org’s int8 and nvfp4 builds of both checkpoints are starter models. Black Forest Labs publishes an fp8 build (fp8r) and an nvfp4 build of each as well, in the variants/ folder of its repositories. They are not starter models, because Klein’s and Klein Base’s files are both called model.safetensors. Install one by URL in the Model Manager, then rename it so the models can be told apart. The URLs are pinned to the revisions InvokeAI was checked against: the Klein file was loaded in full, the Klein Base file compared with it by its header.

  • Klein: https://huggingface.co/black-forest-labs/flux-3-image-klein/resolve/337337621b8526e120f2275d250242f4a6bedd75/variants/fp8r/model.safetensors
  • Klein Base: https://huggingface.co/black-forest-labs/flux-3-image-klein-base/resolve/3f7fa5ee22ca1d5a5cc095ac7cc96e6a173b4c86/variants/fp8r/model.safetensors

Like every Black Forest Labs repository, these need your HuggingFace token. For nvfp4, prefer the Comfy-Org starter model to variants/nvfp4/: InvokeAI turns Black Forest Labs’ file into exactly Comfy-Org’s bytes while loading it, an extra pass over the weights on every load.

  • int8 keeps its quantized layers in int8 on every GPU and decodes them on every step. On an RTX 30-series or newer, int8 Compute multiplies them in int8 instead.
  • nvfp4 keeps 33 of the 43 transformer blocks in 4 bits and decodes them on every step, on every GPU.
  • fp8r stores fp8 weights with one scale per row. With FP8 Storage, which installing it switches on, or with fp8_compute, the weights stay fp8; otherwise they are expanded to bf16 as the model loads.

FP8 Storage does not apply to the int8 and nvfp4 builds: their quantized layers are smaller already, and the layers they keep in bf16 stay bf16. The Model Manager can still show the toggle as on for an nvfp4 build, because installing switches it on for any file holding fp8 numbers, and nvfp4’s block scales are fp8. It has no effect there. Other quantized files, such as AWQ or bitsandbytes exports or nvfp4 files from other tools, are refused at install with a message saying why.

Reference images

Section titled “Reference images”

Add up to ten reference images on the Generate tab or the Canvas and describe the edit in the prompt. No extra model is needed. A single reference is used at up to 4 MP; with several, each is limited to 1 MP.

FLUX.3 names its references in the prompt as <ref_image_0>, <ref_image_1> and so on, for example The fox from <ref_image_0> sitting next to the fox from <ref_image_1>. Each reference card shows its tag; click the tag to copy it. Only enabled cards with an image are numbered, so turning a card off renumbers the cards below it.

In the workflow editor, wrap each image in a Kontext Conditioning - FLUX node and connect them, or a collection of them, to the Reference Images input of Denoise - FLUX.3.

On Nvidia GPUs reference images are encoded whole, as in the reference pipelines, unless the card is too small for a large reference (a 4 MP reference needs about 8.5 GB to encode whole, so cards below 24 GB tile it). On AMD GPUs and Apple Silicon, where the encoder’s attention would need memory that grows with the square of the image size, they are always encoded in 512 px tiles. Tiling keeps memory bounded but changes the edit slightly.

LoRAs

Section titled “LoRAs”

FLUX.3 LoRAs install like any other and appear under Concepts in the Generate panel. Install the LoRA’s .safetensors file, for example by pasting its download URL into the Model Manager, or a Diffusers LoRA folder (pytorch_lora_weights.safetensors). A LoRA may name the transformer’s layers in either of two ways:

  • diffusers’ module names: under transformer., as diffusers’ and SimpleTuner’s trainers save a pipeline’s LoRA; without a prefix, as diffusers saves the transformer’s own adapter (save_lora_adapter) and PEFT a model’s state dict, which carries the adapter’s name in each key (lora_A.default.weight); or under base_model.model., as PEFT saves an adapter;
  • Black Forest Labs’ native module names, under diffusion_model. as ai-toolkit writes them and ComfyUI conversions store them.

A per-layer .alpha in the file sets that layer’s scale. A layer without one takes the scale PEFT gives it from the PEFT settings diffusers saves in the file’s header: lora_alpha divided by the rank, or by the rank’s square root with rsLoRA. A pipeline’s save keys them transformer.r, transformer.lora_alpha and so on, and the transformer’s own save writes them without the prefix. A header with both is read by its transformer. settings. A file whose header sets the rank or alpha per layer (rank_pattern, alpha_pattern) is refused.

Klein and Klein Base share one transformer, so a LoRA trained on either runs on both; most published FLUX.3 LoRAs are trained on Klein Base. How well one holds up at Klein’s step count depends on the LoRA.

  • LoRAs change the transformer only. A file that also has text-encoder layers is refused.
  • Low-rank (lora_A/lora_B or lora_down/lora_up), DoRA, LoKR and LoHA layers are recognized, and so are full weight differences (diff) on the transformer’s linear layers. LoKR and LoHA layers (lokr_* and hada_* parameters) load under the diffusers or Black Forest Labs module names above, in a file without diffusers’ PEFT header. LyCORIS’s own flattened key names (lycoris_…, as SimpleTuner’s LyCORIS output writes them) are not recognized, so such a file does not install as a FLUX.3 LoRA. A PEFT LoKr or LoHa adapter saved with diffusers’ header (peft_type LOKR or LOHA) is refused at install: how PEFT scales those layers is not verified against InvokeAI’s.
  • A layer on Klein’s flow-map embedder (ref_time_in) has no counterpart in Klein Base and is skipped there, with a warning in the log.
  • On GGUF transformers, and with FP8 Storage on, a LoRA runs alongside the weights rather than being merged into them.
  • A FLUX.3 LoRA installs only if all of it applies: every layer it targets exists in the FLUX.3 transformer, is complete and has the shape of the weight it changes. One with any other part is refused at install, with a message naming what does not apply. That includes distillation extracts that change norm scales or add the flow-map embedder (delta.* tensors, set_weight), such as terminusresearch’s Klein extract: to sample with distilled weights, install FLUX.3 Klein itself.
  • A LoRA is recognized as a FLUX.3 LoRA by at least one module that only FLUX.3’s transformer has: its mode blocks, modulations, embedders or the feed-forward layers (ff.linear_in, ff.linear_out) of its single blocks. A LoRA that changes only modules other transformers share, such as the attention layers of the single blocks (attn.to_q and the like), is not recognized as a FLUX.3 LoRA. It is registered as an unknown model, which cannot be used as a LoRA, or, with allow_unknown_models off, refused at install.
  • PDD few-step LoRAs carry per-step output heads (proj_out.weight or pdd.heads), which PDD’s own sampler fuses per jump. InvokeAI loads such a LoRA without them and says so in the log. Use it on Klein Base with CFG Scale 1.0 and 4 to 8 steps; results differ from those of PDD’s own sampler.
  • LoRAs installed with an earlier version of InvokeAI were registered as FLUX.1 LoRAs or as unknown models. Select one in the Model Manager and use Re-identify model to register it as a FLUX.3 LoRA.

Canvas

Section titled “Canvas”

Image-to-image, inpainting and outpainting work on the Canvas as they do for FLUX.2. Using the canvas itself as a reference image is a manual step: create a reference image from the bounding box.

Layout boxes from regional guidance

Section titled “Layout boxes from regional guidance”

On the Canvas, each enabled Regional Guidance layer becomes one box in the prompt. The layer’s Positive prompt describes what goes in the box, and the box is the rectangle around everything painted on the layer inside the generation frame. The shape does not matter, and separate painted areas on one layer share one box. A layer without a positive prompt is left out.

Without reference images, each box places an object. With reference images, FLUX.3 edits them, and each box says where its content goes in the output: the boxes become edit rows with "from": "target" (see below).

FLUX.3 has one kind of box, so the layer offers no Region type. Regional negative prompts, auto-negative and regional reference images are not used with FLUX.3; the layer hides its negative prompt and auto-negative controls. When a layer with a positive prompt has paint inside the generation frame, the main prompt cannot be blank: Invoke is disabled with FLUX.3 needs a prompt to place regional guidance in its layout. Enter a prompt or disable the regional guidance layers.

The boxes are added when the generation runs, as the box table described below, so dynamic prompts and batches vary the prompt in front of them. With the prompt upsampler on, the upsampler receives the boxes instead and keeps them in the box table it writes. The caption FLUX.3 encoded is saved in the image’s metadata as flux3_caption; recalling the image restores the prompt you typed.

Layout and box edits in the prompt

Section titled “Layout and box edits in the prompt”

FLUX.3 reads a layout as the caption, one space, and a JSON list of rows, the box table, at the end of the prompt.

Hand-written tables and dynamic prompts

A table written into the prompt by hand reaches FLUX.3 from the workflow editor and through the API. In the Generate panel and on the Canvas, every prompt that contains { and } goes through dynamic prompts, which read the braces as variant syntax and remove them, so a table written there does not reach FLUX.3 as a table, and boxes from regional guidance start a table of their own after it. Those boxes are added after dynamic prompts have run and are not affected.

Boxes are [y_min, x_min, y_max, x_max] in whole numbers from 0 to 1000 across the image, with (0, 0) at the top left. An object row places an object:

An edit row, {"id", "from", "src_bbox", "tgt_bbox", "desc"}, takes an object from a reference image ("from": "ref_image_0") or adds a new one ("from": "target", with "src_bbox": null): src_bbox is where it is in the reference, tgt_bbox where it goes in the output. Regional guidance writes only object rows and target rows.

Without regional guidance, InvokeAI adds nothing to the prompt. A list at the end of the prompt whose items are not all rows like these, such as ["SALE"], is part of the caption. When boxes are added to a prompt that already ends with a box table, its rows are kept, edit rows included, and the new rows follow them with ids numbered after the highest obj_N.

Prompt upsampler model

Section titled “Prompt upsampler model”

FLUX.3 Klein works best with long, detailed captions. Black Forest Labs publishes a prompt upsampler that writes them: a 9B vision-language model, fine-tuned from Qwen3.5-9B and released under Apache-2.0. InvokeAI installs it as a Text LLM:

Starter modelDownloadSource
FLUX.3 Prompt Upsampler≈ 17.5 GiB (bf16)black-forest-labs/flux-3-image-klein-pup, not gated
FLUX.3 Prompt Upsampler (int8)≈ 9.1 GiBComfyUI’s int8_convrot file from the gated flux-3-image-klein-comfy repository

Use it in two places. Expand Prompt has a built-in system prompt for it and rewrites your text prompt in the prompt box before you generate; in the Generate panel it does not send the upsampler your reference images. The prompt upsampler in generation runs it inside every generation, with the reference images and Regional Guidance boxes.

The int8 file takes about 10.7 GiB once loaded, against 17.5 GiB for the bf16 model, because its language model keeps its weights in int8; it dequantizes them for every token it generates. With int8 Compute on, an NVIDIA GPU runs the language model’s layers on its int8 tensor cores instead. The vision tower’s layers, 108 of the 308 int8 layers, always dequantize; they run once per prompt with an image. Measured on an RTX 4090 (24 GB) through Expand Prompt with Black Forest Labs’ t2i and i2i system prompts, captions of 237–305 tokens, the model already loaded, the default 3 GB of working memory and reserve_vram_gb: 1:

BuildLoaded, all on the GPUTokens/s, text promptTokens/s, prompt with an imageVRAM peak (nvidia-smi, with the desktop)
bf16 folder17.5 GiB21.318.719.7 GiB
int8 file10.7 GiB8.98.612.8 GiB
int8 file, int8 Compute on10.7 GiB14.514.412.8 GiB

The first expansion after a start also loads the model: it took 21.3 s instead of 13.0 s for the same caption with the bf16 model, and 45 s instead of 34 s with the int8 file. After int8 Compute was turned on, the first prompt with an image took about 8 s longer while the kernels were tuned for its longer prompt; the tuning is kept on disk.

The bf16 model is fast only while all of it is on the GPU: what does not fit is streamed in for every token. On the same card with 5 GB of working memory and the same 1 GB reserve, only 89 % of it fit, and it generated 4.2 tokens/s instead of 21.3. To keep the model entirely on the GPU, lower device_working_mem_gb (on the 4090, the default 3 GB left room for the bf16 model) or use the int8 file, which fit entirely in both runs.

ComfyUI’s w4a8 build and single files in fp8 scaled, nvfp4 or mxfp8 are refused at install, and a GGUF of the upsampler is not recognized; Model Format Support lists what loads.

Before this release, InvokeAI did not install the upsampler as a Text LLM: the folder was not identified, and both ComfyUI single files, bf16 and int8, were identified as Qwen3.5 encoders. Use Re-identify model in the Model Manager on such an install.

Prompt upsampler in generation

Section titled “Prompt upsampler in generation”

The prompt upsampler can run as part of every FLUX.3 generation. It rewrites your prompt into the long caption FLUX.3 is trained on, and the text encoder then encodes that caption. Install one of the upsampler models first.

How to use: switch on Prompt upsampler in the Render section of the Generate panel for a FLUX.3 model. It is off by default. The Prompt Upsampler slot is always part of Components for FLUX.3 models and is required only while the switch is on: Invoke is blocked until you pick a Text LLM that reads images there. Choosing another model family clears the pick like any other component; the switch setting is kept. The slot lists every installed Text LLM that reads images, but the system prompts are the ones the Black Forest Labs upsampler was trained with, so pick FLUX.3 Prompt Upsampler or FLUX.3 Prompt Upsampler (int8). The switch works in Generate and on the Canvas.

Only the positive prompt is rewritten. The negative prompt of Klein Base with CFG is encoded as you wrote it.

What the upsampler sees

Section titled “What the upsampler sees”

The upsampler gets what the generation has, and the mode follows:

  • Prompt only: it expands the prompt into a caption.
  • Prompt and reference images: an edit. It writes the edit instruction from the images, which it sees in the order they are attached. They are prepared as Black Forest Labs does: over white, 1 MP for one image, 724² each for two, 512² each from three, saved as JPEG at quality 92.
  • Either of these with a layout: there are Regional Guidance layers on the Canvas, or the prompt ends with a box table.

With a layout, the ids and boxes of the regions, and of the rows of a box table you typed at the end of the prompt, are kept exactly in the box table the upsampler returns. The descriptions are the upsampler’s: the text you typed for a region tells it what goes there, but the row’s description in the caption is what it wrote. It may add rows of its own for other elements of the scene. Without reference images the regions are object rows; with reference images they are rows that place new content in the output, the same rule as without the upsampler. A blank prompt with regions is refused, as it is without the upsampler.

Metadata and recall

Section titled “Metadata and recall”

The caption that was encoded is saved in the image’s metadata as flux3_caption, and the upsampler model as flux3_prompt_upsampler. Recalling the image restores the prompt you typed, not the caption, turns the switch on and selects the model if it is installed. Recalling a FLUX.3 image made without the upsampler turns the switch off and keeps your model pick.

Repeatability and cost

Section titled “Repeatability and cost”

Decoding is greedy, so on the same machine and settings the same prompt, images, regions and model give the same caption. Another GPU, driver or torch version, or another attention_backend, can change a caption after some tokens, and so the image that the recalled settings give. When only the seed, or another setting outside the upsampler’s inputs, changes, the caption comes from the node cache and the upsampler does not run again. Every new prompt is one upsampler run, each Dynamic Prompts variant included.

The upsampler is moved out of VRAM when its run is over, so the text encoder and the transformer do not share VRAM with it. It stays in RAM if the RAM cache has room. Once the upsampler is writing, a cancel stops it between two tokens; a cancel while its model is still loading takes effect when the load is done.

Measured on an RTX 4090 (24 GB) on Windows with Klein bf16 as a single file at 1024 × 1024 and 16 steps, the fp8 Qwen3-VL 4B encoder, the default working memory, reserve_vram_gb: 1 and no other program computing on the GPU (its utilization was 0-6 % before each run). The desktop and other open programs still held some VRAM. Each figure is the median of three runs after one warm-up.

  • The upsampler node alone, bf16 model already in the RAM cache: 15.9 s for a text prompt (a caption of 300 tokens), 13.6 s with one reference image (224 tokens), 14.0 s with two (228 tokens), 27.0 s for a layout with two regions (649 tokens) and 16.2 s for a layout with one reference image and one region (287 tokens). Each includes about 2.5 s to move the model from RAM into VRAM. VRAM peaked at 19.5-20.3 GiB by nvidia-smi, of which about 1.8 GiB was held by the desktop.
  • The upsampler node alone, int8 file, without int8 Compute: 34.5 s for the text prompt, 32.8 s with one reference image and 64.0 s for the layout with two regions. VRAM peaked at 13.5-14.3 GiB, of which about 2.4 GiB was held by the desktop and other open programs.
  • A whole generation with the bf16 upsampler and max_cache_ram_gb: 40: a text prompt took 8.4 s without the upsampler and 28.6 s with it; an edit of one reference image took 15.6 s without and 33.7 s with it. The upsampler added about 18-20 s per new prompt.
  • A cancel took effect 0.5 s after it was requested. A repeat with unchanged inputs came from the node cache in under a second, without loading the model.

The models you use together should fit in the RAM cache. Unset, max_cache_ram_gb is half the system RAM minus 2 GB, but with a dedicated GPU it is capped at the GPU’s VRAM minus device_working_mem_gb: about 21 GB on a 24 GB card with the default working memory. On such a card the default holds neither of the sets given next, and models are read from disk again for every new prompt until you set max_cache_ram_gb higher, system RAM permitting. Loaded, the bf16 upsampler is 17.5 GiB, the bf16 transformer 10.3 GiB, the fp8 text encoder 4.1 GiB and the VAE 0.2 GiB: 32.1 GiB together, or 25.3 GiB with the int8 upsampler (10.7 GiB). With max_cache_ram_gb: 24 the bf16 set did not fit: models were dropped from the RAM cache and read from disk again for every new prompt, and the same text-prompt generation took 40.5 s instead of 28.6 s. Size max_cache_ram_gb for the models you use together, or use the int8 upsampler or a smaller transformer build.

Fidelity to the reference

Section titled “Fidelity to the reference”

The node follows diffusers’ implementation: greedy decoding and no presence penalty, which Black Forest Labs’ own reference applies for text-to-image. For a text prompt, one and two reference images, and a layout with and without a reference image, the caption matched diffusers’ token for token when diffusers ran with the same attention kernel order as InvokeAI.

PiD super-resolution decode

Section titled “PiD super-resolution decode”

FLUX.3 latents are FLUX.2 latents, so the FLUX.2 PiD decoders decode them. See PiD Super-Resolution Decode.

Main Model - FLUX.3Loads the transformer, encoder and VAE
Apply LoRA - FLUX.3 / Apply LoRA Collection - FLUX.3Apply one LoRA, or a collection of them, to the transformer
Prompt Upsampler - FLUX.3Writes the caption FLUX.3 encodes with the prompt upsampler. Takes the prompt, the upsampler model, optional reference images and optional regions. It takes the place of Layout Prompt - FLUX.3, and its Reference Images input takes the same collection as the denoise node’s
Layout Prompt - FLUX.3Adds boxes to a prompt as its box table, or to the table it already ends with: object rows, or with Edit Targets on, rows that place new content in the output of an edit. Each region is a description and a box [y_min, x_min, y_max, x_max] from 0 to 1000. Generate and Canvas graphs pass the prompt through it, turn on Edit Targets when reference images are attached, and fill its regions from regional guidance on the Canvas; the regions input has no editor widget
Prompt - FLUX.3Encodes the prompt
Denoise - FLUX.3Runs the diffusion; takes the VAE, optional reference images and, for Klein Base, CFG and a negative prompt
Latents to Image - FLUX2 / Image to Latents - FLUX2VAE decode / encode

Denoise - FLUX.3 has no scheduler input: Klein steps its own flow map and Klein Base samples with Euler, as in the reference implementation.
